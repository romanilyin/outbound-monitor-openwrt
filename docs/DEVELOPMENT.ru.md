# Разработка и сборка пакетов

[English README](../README.md) · [Русский README](./README.ru.md) · [Development in English](./DEVELOPMENT.md)

## Структура репозитория

| Путь | Назначение |
| --- | --- |
| `outbound-monitor/` | Сборщик, CLI, конфигурация UCI и служба procd |
| `luci-app-outbound-monitor/` | JavaScript/CSS LuCI, методы rpcd и ACL, меню, каталоги gettext |
| `install.sh` | Публичный установщик пакетов из GitHub Releases |
| `scripts/install-local.sh` | Файловый установщик; включается в исходный архив как `install.sh` |
| `scripts/make-bundle.py` | Воспроизводимый архив для установки из исходников |
| `scripts/build-sdk-packages.sh` | Сборка APK/IPK в соответствующем OpenWrt SDK |
| `scripts/ci/` | Статические проверки и сборка `ucode` для компьютера разработчика |
| `tests/` | Тесты интерфейса, ядра и изолированного сбора данных |
| `VERSION` | Публичный тег релиза в формате `YYYY-M-D-N` |

Три пакета релиза — `outbound-monitor`, `luci-app-outbound-monitor` и `luci-i18n-outbound-monitor-ru`. Они содержат скрипты и не зависят от архитектуры процессора. Нативные зависимости должны быть объявлены в метаданных пакетов и поступать из соответствующих репозиториев OpenWrt.

Работа на роутере проверена для OpenWrt 25.12.4; см. [исходный отчёт](./VERIFICATION.md). Матрица SDK для релизов охватывает 25.12.4 и 24.10.6. Успешная сборка SDK не означает проверку версии 24.10 на оборудовании.

## Проверки

Из корня репозитория, с Python 3, Node.js и совместимой установкой `ucode`:

```sh
python3 scripts/ci/static-checks.py
node --test --test-isolation=none tests/ui.test.cjs tests/i18n.test.cjs
ucode tests/core.uc
ucode tests/podkop.uc
ucode tests/runtime.uc /tmp/outbound-monitor-runtime
ucode tests/network.uc
ucode tests/update.uc
```

В CI для подготовки `ucode` используется `scripts/ci/build-ucode.sh`. Рабочему коду нужны модули `fs`, `uci` и `digest`. Проверки shell, JSON, синтаксиса LuCI, переводов и метаданных релиза относятся к статическим; поведение проверяется отдельными тестами интерфейса, ядра и интеграции.

Изолированные проверки сбора и синтаксиса на роутере:

```sh
python3 scripts/check-router.py --env /path/to/external.env
```

На компьютере разработчика требуется Python-модуль `paramiko`. Внешний файл окружения должен содержать `ROUTER_IP` и `ROUTER_PASSWORD`; `ROUTER_USER` и `ROUTER_PORT` необязательны. Не включайте его в репозиторий или релиз. SSH host key сохраняется локально в `.local/known_hosts`.

`check-router.py` загружает тестовые исходники в `/tmp/outbound-monitor-check`, компилирует `ucode`, проверяет синтаксис shell и запускает изолированные сценарии сбора с заглушками запросов, идентичности процесса и привязки ссылок podkop. Он не устанавливает плагин и не перезапускает службы. Проверяйте успешные и неудачные пробы, ошибки API, устойчивую идентичность ссылок, перестановку/замену, изменения конфигурации до применения и во время сбора, отсутствие секретов, классификацию прямых проб и ограничения DNS-результатов.

При реальной проверке роутера также проверьте LuCI на английском и русском, метрики сравнения, оба цвета отказов, время DNS-проверки, выбор периода, экспорт, тёмную тему, узкий экран, сбор по расписанию и обновление. Запишите тип установки — исходники или пакеты, версию OpenWrt и точную ревизию. Не публикуйте адреса частного роутера, учётные данные и VPN-endpoint в скриншотах и отчётах.

## Сборка SDK

На Linux-компьютере с установленными зависимостями OpenWrt SDK:

```sh
scripts/build-sdk-packages.sh 25.12.4
scripts/build-sdk-packages.sh 24.10.6
```

Скрипт использует соответствующий SDK x86/64. Пакеты проекта не зависят от архитектуры; нативные `ucode`, `curl` и прочие зависимости из целевой архитектуры SDK в них не включаются. OpenWrt 25.12.4 создаёт APK, а 24.10.6 — IPK.

Сборка в готовом SDK нужной версии с доступным LuCI feed, из корня этого репозитория:

```sh
ln -s "$PWD" "$SDK/package/outbound-monitor-openwrt"
cd "$SDK"
make defconfig
make package/outbound-monitor/compile package/luci-app-outbound-monitor/compile V=s
```

Сохраняйте структуру всего репозитория: Makefile сборщика обращается к `../VERSION` и `../install.sh`. Копирование только двух каталогов пакетов теряет эти файлы. Для релиза должен быть выбран и русский перевод LuCI. Полную сборку всех трёх пакетов выполняют скрипт сборки и CI.

## Инварианты идентичности и измерений

`core.uc` всегда вычисляет ID графика как SHA-256 полной канонической конфигурации outbound с учётными данными без верхнеуровневого тега. `podkop.uc` сопоставляет `proxy_string` тегу `section-out`, позиции URLTest/selector-списков — тегам `section-N-out`, а VPN-секции — разрешённым парам тег/интерфейс. `link_hash` — хеш наблюдаемой ссылки без пробелов по краям и части после `#`. Это только метаданные: никогда не используйте их для поиска или назначения истории учётных данных и не сохраняйте исходную ссылку. Изменения только URI, не меняющие сгенерированный outbound, не разделяют график. Дубликаты идентичного соединения объединяют теги/группы и используют один текущий API-псевдоним.

Перепривязка должна обновлять текущий тег, подпись, тип, сервер, интерфейс и группы, сохраняя измерения. Миграция старой истории сравнивает полный прежний хеш с учётными данными с текущей конфигурацией, подставляя старый тег; не объединяйте по одному серверу и не выбирайте неоднозначное соответствие. При обновлении сохраняйте прежний runtime-отпечаток outbounds. Версия обнаружения 2 один раз принимает расширенный отпечаток метаданных podkop; последующие изменения на том же процессе sing-box отклоняются до перезапуска. Проверяйте оба отпечатка повторно после проб. Схема ID не меняется после рестарта; соответствие JSON процессу остаётся документированным допущением, но хеш неприменённой ссылки UCI не может переназначить историю.

`runtime.uc` определяет единственный живой процесс `sing-box run` по PID и времени запуска; кратковременные команды check/version/help не считаются дополнительными серверами. Тесты используют искусственные каталоги proc. Ошибки сборщика различают смену идентичности процесса, JSON-конфигурации и метаданных podkop, не называя любое изменение перезапуском службы.

Формат измерения — `[timestamp, status, delay]`:

| Статус | Значение | График/статистика |
| --- | --- | --- |
| `1` | Успешная VPN-проба | Задержка в мс; участвует в метриках задержки |
| `0` | Отказ VPN-пробы | Красная точка −10; участвует в проценте отказов VPN |
| `−1` | Неизвестно/ошибка управления | Пропуск; исключён из метрик |
| `−2` | Вероятный общий сетевой сбой | Синяя точка −10; исключён из метрик и серии отказов VPN |

Процент отказов VPN делит число проб `0` на число проб `0 + 1`. Среднее, генеральная дисперсия (деление на `n`) и стандартное отклонение используют только успешные задержки. Неизвестные результаты, пропуски и `−2` исключаются; одна успешная проба даёт нулевую дисперсию. При сравнении ключей показывайте выбранный период, число и свежесть измерений.

## Прямые контрольные пробы и необязательная DNS-диагностика

Сборщик использует подходящий существующий `direct` outbound для двух HTTPS-проверок: `generate_204` gstatic и Cloudflare; `network.uc` классифицирует результаты. Отклоняйте VPN-detour и унаследованные `route.default_interface`/`route.default_mark`. Общий сбой отмечается только при отказе обеих проверок и всех VPN-проб. Если при отказе обеих прямых проверок хотя бы одна VPN-проба успешна, результат смешанный. DNS-резолвер и даже системный маршрут по умолчанию могут использовать VPN: это проверка существующего direct-outbound, а не доказательство доступности физического канала провайдера.

При `dns_check=1` и уже установленном IPRegion отказ обеих проверок запускает необязательную DNS-диагностику, в том числе при смешанном результате. Запускайте IPRegion с `--no-uci`, тайм-аутом `2`, повторами `0`, отдельным `IPREGION_RUNTIME_DIR` и общим ограничением 25 секунд. Используйте доступные резолверы/транспорты установленной версии, включая UDP/TCP и DoT/DoH при их поддержке. Принимайте DNS-схемы v1 и v2 и сохраняйте краткие статусы транспортов без допущения о фиксированном числе резолверов. Не добавляйте пакетную зависимость, не устанавливайте IPRegion и не меняйте его настройки. Используется маршрут роутера, который может включать VPN; неудачное сравнение резолверов не доказывает подмену и не определяет виновного провайдера.

Сохраняйте последний краткий DNS-результат и не более 128 последних подробных `network_events`, также ограниченных `retention_days` (максимум семь дней). Не удаляйте сохранённый DNS-результат и его время при отключении проверок или удалении IPRegion. Временные файлы IPRegion изолируйте от его обычной сессии; не запускайте версии без поддержки `IPREGION_RUNTIME_DIR`. JSON-экспорт включает ограниченную историю сетевых событий; этот лимит не должен сокращать историю графиков ключей. Сохраняйте проверки владельца/прав каталога состояния и не записывайте статистику постоянно во флеш.

## Границы LuCI, RPC и обновлений

- Исходные строки на английском должны быть внутри `_('...')`; русский каталог gettext создаёт `luci-i18n-outbound-monitor-ru`. Не переводите имена полей API и идентификаторы outbound.
- Объект rpcd — `luci.outbound-monitor`. ACL должен разрешать только необходимые странице методы, без произвольного выполнения shell-команд.
- `update_status`, `check_update` и `update` не принимают от вызывающей стороны репозиторий, URL или аргументы shell. Проверка и установка запускаются только нажатием кнопки; локальное состояние операции можно опрашивать.
- `/usr/bin/outbound-monitor-update check` и `install` выполняют обновление из фиксированного репозитория `romanilyin/outbound-monitor-openwrt`.
- Обновления используют только стабильные релизы, пакетный установщик и проверку SHA-256. Не добавляйте автоматический фоновый цикл обновления.
- При обновлении сохраняйте UCI-конфигурацию монитора, историю в RAM и состояние автозапуска. Перезапускайте его службу только если она работала или это первая установка; для регистрации RPC используйте `rpcd reload`.

Сборщик не должен менять podkop, sing-box, сеть, firewall, DNS или cron. Сохраняйте описанные в обоих README ограничения: активные пробы влияют на URLTest, а привязка к конфигурации опирается на допущение о соответствии JSON процессу. Ошибки API должны отличаться от отказов отдельных ключей. Секреты не должны попадать в историю, RPC-ответы, журналы или аргументы процессов.

## Архив для установки из исходников

Этот резервный способ копирует файлы и не регистрирует пакеты в `apk` или `opkg`. Для управляемых обновлений и скомпилированного русского перевода используйте пакеты. Интерфейс LuCI исходного архива — английский.

Сборка на компьютере:

```sh
python3 scripts/make-bundle.py
scp -O dist/outbound-monitor-2026-9-23-1.tar.gz root@ROUTER:/tmp/
```

На роутере:

```sh
mkdir -p /tmp/outbound-monitor-install
tar -xzf /tmp/outbound-monitor-2026-9-23-1.tar.gz -C /tmp/outbound-monitor-install
sh /tmp/outbound-monitor-install/install.sh
```

Имя архива соответствует `VERSION`. Его `install.sh` берётся из `scripts/install-local.sh`, а не из корневого загрузчика репозитория. Локальный установщик не скачивает зависимости и останавливается при отсутствии необходимых программ или модулей. Нужны `ucode`, `ucode-mod-fs`, `ucode-mod-uci`, `ucode-mod-digest`, `curl`, `ca-bundle`, `flock`, `luci-base` и `rpcd-mod-ucode`. Сами HTTPS-пробы выполняет sing-box; обновление использует HTTPS-клиент и CA-сертификаты роутера.

## Выпуск релиза

Формат тегов — **`YYYY-M-D-N`**: месяц и день без ведущего нуля, затем порядковый номер выпуска. Первый релиз — `2026-9-23-1`. В метаданных OpenWrt ему соответствуют `PKG_VERSION:=2026.9.23` и `PKG_RELEASE:=1`; поддерживайте согласованность метаданных пакетов и `VERSION`.

Перед созданием тега выполните целевые проверки и проверьте итоговый установщик, обновление, метаданные пакетов и перевод интерфейса. Проверьте историю после перестановки/замены, смешанные прямые/VPN-результаты, отсутствие/отключение/тайм-аут DNS-диагностики и ограничения событий в экспорте. Испытайте обновление существующей установки: настройки, история и состояние службы должны сохраниться; ошибка запроса или контрольной суммы не должна приводить к установке непроверенных файлов. Явно указывайте, какие проверки на оборудовании не выполнялись.

Отправка тега запускает матрицу SDK в GitHub Actions для **25.12.4** и **24.10.6**, затем публикацию релиза. Полный релиз содержит:

| Формат | Постоянные имена файлов |
| --- | --- |
| APK | `outbound-monitor.apk`, `luci-app-outbound-monitor.apk`, `luci-i18n-outbound-monitor-ru.apk` |
| IPK | `outbound-monitor.ipk`, `luci-app-outbound-monitor.ipk`, `luci-i18n-outbound-monitor-ru.ipk` |
| Исходный архив | `outbound-monitor-2026-9-23-1.tar.gz` для первого релиза |
| Контрольные суммы | `SHA256SUMS` для опубликованных файлов |

После публикации убедитесь, что релиз стабильный, все необходимые файлы присутствуют, контрольные суммы скачанных файлов совпадают, а однострочный установщик находит этот релиз. Сохраняйте версионные файлы пакетов, если workflow публикует их рядом с постоянными именами. Не выдавайте незапущенный или упавший workflow за успешную сборку.

Пакеты GitHub находятся вне официальных репозиториев OpenWrt. Установка APK использует `--allow-untrusted`, а загрузки проверяются по `SHA256SUMS` релиза; это проверка соответствия опубликованным файлам, а не отдельная цепочка доверия подписи пакета. Для включения в официальные feeds потребуется отдельно пересмотреть GitHub-обновление и правила упаковки.

## Удаление установки из исходников

Эти команды предназначены только для установки из исходного архива. Пакеты удаляйте через `apk` или `opkg`:

```sh
/etc/init.d/outbound-monitor stop
/etc/init.d/outbound-monitor disable
rm -f /etc/init.d/outbound-monitor /usr/bin/outbound-monitor
rm -f /usr/bin/outbound-monitor-update
rm -f /usr/share/outbound-monitor/core.uc /usr/share/outbound-monitor/main.uc
rm -f /usr/share/outbound-monitor/network.uc
rm -f /usr/share/outbound-monitor/update.uc /usr/share/outbound-monitor/update-core.uc
rm -f /usr/share/outbound-monitor/install.sh /usr/share/outbound-monitor/version
rm -f /usr/share/rpcd/ucode/outbound-monitor.uc
rm -f /usr/share/rpcd/acl.d/luci-app-outbound-monitor.json
rm -f /usr/share/luci/menu.d/luci-app-outbound-monitor.json
rm -f /www/luci-static/resources/view/outbound-monitor/status.js
rm -f /www/luci-static/resources/outbound-monitor/style.css
/etc/init.d/rpcd reload
```

Настройки `/etc/config/outbound-monitor` и история остаются. Удаляйте их отдельно, только если они больше не нужны.
